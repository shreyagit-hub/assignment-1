# Git fundamentals
## 1.	Git has three places a change can live: the working directory, the staging area, and the repository. Describe each, and explain what you would lose if the staging area did not exist.
There are three main places for changes in Git. The required changes are made on the working directory, the changes that are to be committed are selected in the staging area, and the committed changes are stored in the repository. If the staging area did not exist, there would be no place for selecting specific changes before committing them as the staging area gives control over what exactly goes into each commit. An example of this is committing a bug while keeping unrelated work as is.

## 2.	<span style="font-family: 'Consolas', monospace;">git init</span> and <span style="font-family: 'Consolas', monospace;">git clone</span> both leave you with a Git repository. Explain what each one actually does, and give a situation where each is the right choice.
<span style="font-family: 'Consolas', monospace;">git init</span> creates a new, empty Git repository in a directory whereas <span style="font-family: 'Consolas', monospace;">git clone</span> copies an existing repository with its files and commit history. Example cases of their uses are: <span style="font-family: 'Consolas', monospace;">git init</span> is used when starting a new project, and <span style="font-family: 'Consolas', monospace;">git clone</span> is used when joining an already existing project.

## 3.	What does a commit store, and why is "committing" not the same as "saving a file"? Why is Git much less useful if <span style="font-family: 'Consolas', monospace;">user.name</span> and <span style="font-family: 'Consolas', monospace;">user.email</span> are unset or wrong?
A commit stores a snapshot (state of the project at a particular time) of the tracked project files. It stores metadata related to the project such as the author, date, message, etc. Git is much less useful if <span style="font-family: 'Consolas', monospace;">user.name</span> and <span style="font-family: 'Consolas', monospace;">user.email</span> are unset or wrong because Git cannot commit reliably to the correct owner if the name and email are wrong, which makes accountability harder.

## 4. <span style="font-family: 'Consolas', monospace;">git status</span>, <span style="font-family: 'Consolas', monospace;">git log</span> and <span style="font-family: 'Consolas', monospace;">git diff</span> answer three different questions. State the question each one answers, and describe a moment in your workflow where you would reach for each.
<span style="font-family: 'Consolas', monospace;">git status</span> lists the state of the files, <span style="font-family: 'Consolas', monospace;">git log</span> displays the commit history, and <span style="font-family: 'Consolas', monospace;">git diff</span> shows the line by line changes. In my workflows, <span style="font-family: 'Consolas', monospace;">git status</span> would be used to check what will be included in a commit, <span style="font-family: 'Consolas', monospace;">git log</span> would be used to understand previous changed, and <span style="font-family: 'Consolas', monospace;">git diff</span> would be used to review the project before staging or committing it.

## 5.	Explain what makes a commit message good. Why is “update” a genuine problem for a team six months later, and when is it worth writing a message body rather than just a summary line?
A good commit message briefly explains the purpose of a change rather than just saying what happened. A message such as “update” becomes unhelpful six months later because it does not explain what was updated or why. A message body is worth writing when the reason for the change, the problem it solves or some decision cannot be explained clearly in the summary line alone.

# Branching, merging, pull requests
## 6.	Explain the relationship between your local repository and <span style="font-family: 'Consolas', monospace;">origin</span>. What do push and pull each move, in which direction, and why is pulling before pushing the habit to build?
The local repository contains the project and its commit history on the personal computer whereas <span style="font-family: 'Consolas', monospace;">origin</span> is the conventional name for the remote repository which is often hosted on GitHub. git push sends local commits to the remote and git pull integrates the received changes into the current branch. Pulling before pushing is a habit to build because it helps to avoid conflicts when multiple people are working on the same project, for example, when someone working on the same project has updated the same file that someone else is working on.

## 7.	<span style="font-family: 'Consolas', monospace;">git fetch</span> and <span style="font-family: 'Consolas', monospace;">git pull</span> are not the same command. What is the difference, and when would you deliberately choose <span style="font-family: 'Consolas', monospace;">fetch</span>?
<span style="font-family: 'Consolas', monospace;">git fetch</span> allows a developer to check what changes have been made to a project before committing them. <span style="font-family: 'Consolas', monospace;">git pull</span> downloads those changes and adds them to the current branch. <span style="font-family: 'Consolas', monospace;">fetch</span> is used deliberately by a person when they need to review the changes made by others working on the project before deciding whether to combine them with their own.

# Branching, merging, pull requests
## 8.	A branch in Git is often described as "just a pointer." Explain what that means, and explain concretely what goes wrong on a team when everyone commits directly to <span style="font-family: 'Consolas', monospace;">main</span>.
A branch in Git is often described as "just a pointer" because it allows developers to work on separate things without immediately changing the main branch. If everyone on a team commits directly to <span style="font-family: 'Consolas', monospace;">main</span>, unfinished or broken code can affect the shared project and reviewing changes becomes more difficult. Feature branches and Pull Requests allow work to be tested and reviewed before it is integrated into the <span style="font-family: 'Consolas', monospace;">main</span> branch.

## 9.	A merge conflict happens when two branches change the same lines of the same file. Explain why Git cannot resolve this automatically, what the <<<<<<<, =======, >>>>>>> markers mean, and what you must do to finish the merge.
Git cannot resolve it automatically because Git cannot decide which of the conflicting changes to keep on its own. When a conflict happens, Git inserts conflict markers (<<<<<<<, =======, and >>>>>>>) directly in the file as an indicator for the problems. <<<<<<< marks the beginning of the conflicting code from the current branch, ======= separates the current branch’s changes from incoming changes and >>>>>>> marks the end of the conflicting code from the incoming branch. A file should be edited to keep the correct result, the conflict markers should be removed and the resolved file should be staged before completing the merge.

## 10.	You could merge a branch locally with <span style="font-family: 'Consolas', monospace;">git merge</span> and <span style="font-family: 'Consolas', monospace;">push</span>. What does opening a Pull Request add that a local merge does not? What belongs in a PR description?
A Pull Request is a request that is sent before integrating any changed into the main branch. Unlike a local merge, a pull request lets the team review, discuss, and test the changes in the code before it gets merged. A PR description contains what changed, why it was needed, and how to test it.

# Issues
## 11.	Explain the purpose of labels and assignees on an Issue, and what <span style="font-family: 'Consolas', monospace;">Fixes #12</span> in a merged PR does. Why is linking work to Issues better than closing them by hand?
Labels categorize what the Issue is about whereas assignees show the person responsible for working on the Issue. Putting <span style="font-family: 'Consolas', monospace;">Fixes #12</span> in a merged PR automatically closes Issue #12 as soon as the code is merged. Linking work to Issues is better than closing them by hand as it saves time, prevents forgotten open issues and creates a clear record showing which code fixed which problem.

# Project structure, environments, secrets
## 12.	Why should <span style="font-family: 'Consolas', monospace;">.gitignore</span> be one of your first commits? If a file is already tracked, does adding it to <span style="font-family: 'Consolas', monospace;">.gitignore</span> stop Git from tracking it — and if not, what do you do instead?
A <span style="font-family: 'Consolas', monospace;">.gitignore</span> file tells Git which untracked files or directories it should normally ignore. Creating it early prevents unnecessary or sensitive files from accidentally entering the repository. However, <span style="font-family: 'Consolas', monospace;">.gitignore</span> does not stop tracking a file that Git already tracks. For that, the file must be removed from Git's index (like with <span style="font-family: 'Consolas', monospace;">git rm --cached filename</span>) while keeping the local file.

## 13.	Explain the difference between <span style="font-family: 'Consolas', monospace;">.env</span> and <span style="font-family: 'Consolas', monospace;">.env.example</span>, and why they get opposite treatment. If a real API key was committed three weeks ago, why is deleting it in a new commit not a fix, and what should actually be done?
A <span style="font-family: 'Consolas', monospace;">.env</span> file contains machine-specific environment variables and can hold secret keys, so they are usually not included in Git. Instead, a <span style="font-family: 'Consolas', monospace;">.env.example</span> file has the placeholder values for the sensitive information in a <span style="font-family: 'Consolas', monospace;">.env</span> file which makes it suitable for committing. If a real API key was committed, deleting it in a new commit is not enough because it remains in Git history. The key should be revoked immediately or the entire commit history should be cleared if a key has been committed.

## 14.	What problem do a virtual environment and <span style="font-family: 'Consolas', monospace;">requirements.txt</span> solve together? Why is <span style="font-family: 'Consolas', monospace;">venv/</span> itself never committed, when requirements.txt always is?
A virtual environment isolates a project's installed packages from other projects and the <span style="font-family: 'Consolas', monospace;">requirements.txt</span> file records the dependencies needed to recreate the environment required for a project. Together, they prevent version clashes and ensure everyone uses the exact same software setup <span style="font-family: 'Consolas', monospace;">venv/</span> is normally excluded because it contains a large, machine-specific installation, but <span style="font-family: 'Consolas', monospace;">requirements.txt</span> is always included because it records the dependencies needed to run the code.

## 15.	Explain what <span style="font-family: 'Consolas', monospace;">git push --force</span> does to a shared branch and whose work it can destroy. How does <span style="font-family: 'Consolas', monospace;">--force-with-lease</span> behave differently, and why is that safer?
<span style="font-family: 'Consolas', monospace;"> git push --force</span> overwrites the remote branch reference with the local branch history, potentially removing commits that other team members have pushed. <span style="font-family: 'Consolas', monospace;">git push --force-with-lease</span> performs a similar history update but checks that the remote branch has not changed unexpectedly from the version that is known. It is safer because it usually rejects the push if someone else has updated the branch, although it still rewrites shared history and should be used carefully.
